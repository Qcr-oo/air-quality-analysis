```

common.py        ← 输出工具（解决 Windows 控制台编码问题）

web/             ─── 第三阶段：Spring Boot 后端 + ECharts 前端
```

## 为什么分这么多文件，不写一个大脚本？

**每个 step 只做一件事。** 好处：

1. **出错容易定位** —— 报错在 `step3_clean.py`，就说明是清洗环节的问题，不用在 3000 行里找
2. **可以单独重跑** —— 改了清洗逻辑只重跑 step3，不用从头再跑一遍
3. **数据流是可见的** —— 每一步的产出都落成文件，能打开看

> **被问到就这样答**："我把流程拆成独立的脚本，每个脚本只做一件事，产出中间文件。
> 这样调试时能快速定位问题，也能单独重跑某一步，不用整条链路重来。"

## `config.py`（76 行）—— 集中配置

### 这个文件在解决什么

**初学者最常见的坏习惯：把路径写死在每个脚本里。**

```python
# 坏做法：散落在各个文件里
pd.read_csv(r"F:\myprogect\01-毕业设计\05-数据集\2018_air_city_hour.csv")

# 好做法：集中在 config.py
from config import raw_file
pd.read_csv(raw_file(2018))
```

**为什么重要**：数据挪个位置，只需要改 `config.py` 一处，不用担心漏改某个脚本。

### 🔴 关键代码（这里踩过坑）

```python
SRC_DIR = os.path.dirname(os.path.abspath(__file__))       # .../07-系统实现/src
BASE_DIR = os.path.dirname(SRC_DIR)                        # .../07-系统实现
PROJECT_DIR = os.path.dirname(BASE_DIR)                    # .../01-毕业设计

RAW_DIR = os.path.join(PROJECT_DIR, "05-数据集", "空气质量数据")
```

**为什么退两层**：`config.py` 自己在 `src/` 目录里，所以要往上退两层才到毕业设计根目录。

> 🔴 **这个坑我踩过**：一开始只退了一层（退到 `07-系统实现`），
> 结果 `RAW_DIR` 指向了不存在的目录，抽样跑出 0 行。
> **被问到就这样答**："路径是用 `__file__` 反推的，不是硬编码的绝对路径，
> 所以项目整个挪走也不用改代码。这里要注意 `config.py` 在 `src/` 里，要往上退两层。"

## `common.py`（70 行）—— 输出工具

### 这个文件在解决什么

**Windows 中文控制台默认编码是 GBK。** 输出 `✓`、`⚠` 这类符号会直接崩：

```
UnicodeEncodeError: 'gbk' codec can't encode character '\u26a0'
```

### 🔴 关键代码

```python
def enable_utf8():
    for stream in ("stdout", "stderr"):
        s = getattr(sys, stream, None)
        if s is not None and hasattr(s, "reconfigure"):
            try:
                s.reconfigure(encoding="utf-8", errors="replace")
            except Exception:
                pass
```

**两个要点**：
1. `reconfigure(encoding="utf-8")` —— 把标准输出切成 UTF-8
2. `errors="replace"` —— 遇到打不出的字符**用 ? 代替，而不是抛异常**

> **被问到就这样答**："Windows 中文控制台是 GBK 编码，输出 Unicode 符号会让脚本崩溃。
> 我做了两层处理：一是把标准输出切成 UTF-8，二是设置 `errors='replace'`，
> 保证遇到无法编码的字符时降级显示，而不是让脚本挂掉。"

### 🟡 Reporter 类

```python
class Reporter:
    def __call__(self, text=""):
        print(text, flush=True)          # 屏幕
        if self.fh:
            self.fh.write(str(text) + "\n")
            self.fh.flush()              # 文件，立即刷盘
```

**为什么要 flush**：长时间运行的任务（比如 step8 要跑 25 分钟），
不 flush 的话文件缓冲会导致日志"看起来卡住了"，无法从外部观察进度。

### 🔴 关键代码：陷阱 5 去重

```python
def clean(df):
    ...
    # 陷阱 5：按「城市 + 时刻」去重，保留第一条
    df = df.drop_duplicates(subset=["city_code", "datetime"], keep="first").copy()
```

# 第 2 部分：第一阶段（pandas）

## `step1_sample.py`（111 行）—— 抽样

### 核心思路

**先用小样本把逻辑跑通，再上全量。** 1233 万行每次调试等几分钟，效率极低。

### 🔴 关键代码：怎么估抽样间隔

```python
def estimate_step(year, target):
    path = raw_file(year)
    size = os.path.getsize(path)
    with open(path, ...) as fh:
        n = 0; total = 0
        for line in fh:
            total += len(line.encode("utf-8"))
            n += 1
            if n >= 200: break          # 只读前 200 行
    avg = total / n                      # 平均每行多少字节
    est_rows = int(size / avg)           # 用文件大小估总行数
    step = max(1, est_rows // target)    # 算出每隔多少行取一行
    return est_rows, step
```

**为什么要估，不直接数行数？**
**数一遍行数 = 把文件完整读一遍**，那就失去"快速"的意义了。用「文件大小 ÷ 平均行长」可以秒估。

> **被问到就这样答**："估算行数不能真的去数——数一遍就等于读了一遍文件。
> 我用文件大小除以抽样得到的平均行长度来估，只读前 200 行，瞬间出结果。"

### 🟡 为什么这一步不用 pandas

```python
with open(raw_file(y), ...) as fh:
    reader = csv.reader(fh)
    for i, row in enumerate(reader):
        if i % step: continue
        writer.writerow(row)
```

**逐行流式处理，内存占用恒定（几百 KB）**，不会把 1.89 GB 全读进内存。

> **被问到就这样答**："这一步只做「读一行、写一行」，不需要分析能力，
> 所以用纯标准库逐行处理，内存占用是恒定的。工具要选合适的，不是越高级越好。"

### 🔴 关键代码 1：日期解析


**两个要点**：

> **被问到就这样答**："关键是 `errors='coerce'`。如果不加，
> 解析失败会直接抛异常中断；加上之后变成 NaT，我可以统计失败了多少条——
> 这个数字本身就是判断格式对不对的依据（当时 61% 失败，正好印证了格式反了）。"

### 🔴 关键代码 2：用物理常识验证

```python
monthly = df.groupby("month")["AQI"].agg(["count", "mean"])
peak = int(monthly["mean"].idxmax())      # 最高月
low = int(monthly["mean"].idxmin())       # 最低月

if peak in (11, 12, 1, 2) and low in (6, 7, 8):
    print("通过！呈现标准的「冬高夏低」")
```

**这是整份代码里最重要的设计思想**：

> **不能只看"没报错"就算成功，要用一个"结果本该如此"的规律去验证。**

对空气质量数据，最好的验证就是**月度 AQI 必须"冬高夏低"**（冬季供暖 + 逆温，夏季扩散好）。
如果日/月对调了，夏季数据会跑到冬季，曲线一定乱。

> 🔴 **被问到就这样答**："清洗完不能只看程序没报错。我用了一个领域常识来验证——
> 空气质量必然是冬高夏低。我的结果是 1 月 101.3、8 月 56.7，标准 U 形，
> 说明日期解析是对的。如果曲线不符合规律，就说明还有问题。"

## `step5_model.py`（615 行）—— 机器学习

### 🔴 关键代码 1：时序数据必须按时间切分

```python
tr = d[d["year"] == DENSE_YEARS[0]]      # 2017 年训练
te = d[d["year"] == DENSE_YEARS[1]]      # 2018 年测试
```

**为什么不能随机切**：随机划分会把 2018 年的数据混进训练集，
**让模型"见过未来"**，测试分数虚高，上线就崩。**这叫数据泄漏。**

> 🔴 **被问到就这样答**："时序数据不能随机划分训练测试集。
> 随机切会把未来的数据混进训练集，模型见过答案，测试分数虚高。
> 我是用 2017 年训练、2018 年测试，这才是真实场景——用历史预测未来。"

### 🔴 关键代码 2：持续性基线

```python
base = te["aqi_now"]                     # 什么都不算，直接把当前值当预测
bm = metrics(yte_h, base)                # 基线的误差

...训练模型...
mm = metrics(yte_h, pred)                # 模型的误差

improve = (bm["mae"] - mm["mae"]) / bm["mae"] * 100
if improve > 0:
    print("[OK] 模型优于基线")
```

**为什么要基线**：空气质量**自相关性极强**（这一小时和上一小时几乎一样），
所以"直接拿当前值当预测"这个朴素基线往往强得惊人。
**赢不了基线的模型没有存在价值。**

> 🔴 **被问到就这样答**："任何时序预测都必须和持续性基线比。
> 这个基线就是'什么都不算，直接拿当前值当作未来的预测值'。
> 空气污染自相关性很强，这个基线本身就很强——我的 t+24 基线 R² 有 0.35。
> 模型做到 0.60，比基线好 12.9%，这才说明模型有价值。"

### 🔴 关键代码 3：滞后特征的构造顺序

```python
d["aqi_roll24"] = g["AQI"].transform(
    lambda s: s.shift(1).rolling(24, min_periods=12).mean())
```

**注意顺序：先 `shift(1)` 再 `rolling(24)`。**

```python
s.shift(1).rolling(24).mean()   # 正确：过去 24 小时（不含当前）
s.rolling(24).mean()            # 错误：包含当前时刻 → 数据泄漏
```

> 🔴 **被问到就这样答**："滚动平均必须先 shift 再 rolling。
> 如果先 rolling，窗口里会包含当前时刻的值，那就是拿当前预测当前，属于数据泄漏。"

### 🟡 关键代码 4：中文路径导致 joblib 崩溃

## `step6_spark.py`（522 行）—— 分布式处理

### 🔴 关键代码 1：四个环境坑的自动处理

```python
def setup_env():
    # 坑 1：JAVA_HOME 指向空目录 -> 用便携版 JDK
    # 坑 2：SPARK_HOME 版本错配 -> 指向 pip 包自带的 jar
    # 坑 3：中文路径打断启动脚本 -> 建 ASCII 目录联接绕过
    # 坑 4：Python worker 连不回来 -> 指定 PYSPARK_PYTHON + 绑定 127.0.0.1
```

**这一段是纯环境适配代码，功能上不产生任何分析结果，但没有它整个 Spark 都跑不起来。**

> 🔴 **被问到就这样答**（重点讲坑 3，那是最有技术含量的一段）：
> "PySpark 通过 `$SPARK_HOME/bin/spark-submit.cmd` 启动 JVM，
> 而 pip 把包装在 `C:\Users\瞿崇荣\...` 下——**Windows 批处理脚本处理不了中文路径**，
> 报 `ClassNotFoundException: SparkSubmit`。
> 我做了个对照实验：换成纯 ASCII 路径的 Spark 立刻成功，从而锁定是路径问题。
> 解决办法是建一个目录联接（`mklink /J`），把中文路径映射成 ASCII 路径，
> 不需要管理员权限，也不复制数据。"

### 🔴 关键代码 2：显式 schema

```python
schema = StructType([
    StructField("release_date", StringType()),
    StructField("city_code", StringType()),
    ...
])
df = spark.read.option("header", "true").schema(schema).csv(paths)
```

**为什么不用 `inferSchema=true`**：
1. 它会**先扫一遍全量数据猜类型**，多花一倍时间
2. **可能猜错** —— 比如把城市编码 `110000` 猜成整数，但有前导零的编码就丢信息了

> **被问到就这样答**："显式定义 schema 有两个好处：一是 Spark 不用先扫一遍猜类型，
> 只读一遍文件；二是不会猜错——比如城市编码是字符串，如果被猜成整数，
> 带前导零的编码就废了。"

### 🔴 关键代码 3：惰性求值的实证

```python
t0 = time.time()
df = spark.read.option("header", "true").schema(schema).csv(paths)
n_raw = df.count()          # <- 这一行才真正触发读取
t_read = time.time() - t0
```

**`spark.read.csv()` 那行几乎不耗时，是 `count()` 才真正开始读。**
这就是**惰性求值**：transformation 只记录"要做什么"，action 才触发执行。

> 🔴 **被问到就这样答**："Spark 是惰性的。`read.csv`、`filter`、`groupBy`
> 这些 transformation 只是记录执行计划，不会立刻算。
> 只有遇到 `count`、`show`、`write` 这种 action 才真正触发。
> 好处是 Spark 能把一连串操作合并成一个计划统一优化。"

## `step8_mllib.py`（604 行）—— Spark MLlib 建模

### 🔴 关键代码 1：VectorAssembler

```python
assembler = VectorAssembler(inputCols=FEATURES, outputCol="features")
data = assembler.transform(df)
```

**MLlib 和 sklearn 最大的 API 区别**：sklearn 把 `X, y` 分开传，
**MLlib 要求所有特征合成一个 vector 列**，因为它是为分布式设计的。

| sklearn | Spark MLlib |
|---|---|
| `model.fit(X, y)` | `model.fit(df)` |
| `model.predict(X)` | `model.transform(df)` |
| `class_weight` | `weightCol` |
| `cross_val_score` | `CrossValidator` |

### 🔴 关键代码 2：类别权重

```python
freq = {row["label"]: row["cnt"] for row in ...}   # 统计类别频率
weights = {k: total / (n_cls * v) for k, v in freq.items()}   # 权重 = 频率的倒数
wcol = F.create_map([F.lit(x) for kv in weights.items() for x in kv])
with_label = with_label.withColumn("weight", wcol[F.col("label")])
clf = GBTClassifier(...).setWeightCol("weight")
```

**解决了什么问题**：污染天只占 17.5%，是少数类。不加权重时，
模型倾向于**全部预测为"良好"** —— 准确率好看，但污染天几乎全漏报。

**实测效果**：

| | 带权重 | 不带权重 |
|---|---|---|
| 准确率 | 0.8509 | **0.9018** |
| **污染天召回率** | **83.8%** | 56.1% |
| **漏报条数** | 62,530 | **169,494** |

> 🔴 **被问到就这样答**："污染天只占 17.5%，是典型的类别不平衡。
> 不加权重时模型会倾向于全预测成'良好'，准确率有 0.90 看起来不错，
> 但它漏掉了 43.9% 的污染天——将近 17 万条预警没发出去。
> 预警系统的代价是不对称的：误报代价可控，漏报代价高得多。所以我选了带权重的模型，
> 准确率降到 0.85，但漏报率从 43.9% 降到 16.2%。"

### 🔴 关键代码 3：条件聚合（这里踩过坑）

```python
# ❌ 错误写法
F.avg(F.col("is_heating") * F.col("AQI")).alias("heat_aqi")

# ✅ 正确写法
F.avg(F.when(F.col("is_heating") == 1, F.col("AQI"))).alias("heat_aqi")
F.avg(F.when(F.col("is_heating") == 0, F.col("AQI"))).alias("nonheat_aqi")
```

**为什么错**：`avg(is_heating * AQI)` 算的是
`avg(采暖季的 AQI, 其余位置全是 0)` —— **被大量 0 稀释**，结果必然偏小甚至为负。
实测全是 -26 ~ -49，和"采暖季 AQI 更高"的结论**直接矛盾**。

> 🔴 **被问到就这样答**（这个坑值得主动讲）：
> "采暖效应我一开始写成了 `avg(is_heating * AQI)`，这其实是
> `avg(采暖季的AQI, 其余全是0)`，被 0 稀释了，算出来全是负数，
> 和前面的分析结论矛盾。改成用 `when` 做条件聚合才对。
> **教训是：凡是分组算均值，都要检查分母对不对。**"

## `step7_mysql.py`（377 行）—— 结果入库

### 🔴 关键代码 1：先删后建

```python
for name, ddl in DDL:
    cur.execute("DROP TABLE IF EXISTS %s" % name)
    cur.execute(ddl)
```

**为什么不用 `CREATE TABLE IF NOT EXISTS`**：

> **它遇到已存在的表会直接跳过 —— 表结构改了也不会生效。**

我踩过这个坑：改了 `fact_prediction` 的列之后忘了删表，结果插入时报 `Unknown column`。

> **被问到就这样答**："建表用的是先删后建。因为 `IF NOT EXISTS` 遇到已存在的表会跳过，
> 表结构改了也不生效。本项目所有表的数据都来自 CSV，随时可以重建，所以先删更安全。"

### 🔴 关键代码 2：列语义必须对齐

```python
pr = pr.rename(columns={
    "AQI": "current_aqi",        # 当前时刻
    "AQI_t+1": "actual_aqi_t1",  # t+1 的真实值
    "AQI_t+24": "actual_aqi_t24",# t+24 的真实值  <- 和预测值比较的是这个
    ...
})
```

**这是一个真实 bug 的修复**：最初把 `AQI`（当前时刻）当成了 `actual_aqi`，
但 `pred_aqi_t24` 预测的是 **t+24 时刻** —— **拿不同时刻的两个数做减法，误差被严重低估**。

实测（同样 5 万条样本）：

| 比法 | MAE |
|---|---|
| 正确：`|pred_t24 − actual_t24|` | **16.96** |
| 错误：`|pred_t24 − current_aqi|` | **13.21** |

**误差被低估了 28.4%。**

> 🔴 **被问到就这样答**："这里我踩过一个坑。最开始我把 CSV 里的 `AQI` 直接当成了
> 预测目标的真实值，但 `AQI` 是**当前时刻**的，而 t+24 的预测要和 **t+24 的真实值**比。
> 拿不同时刻的两个数相减，误差会被低估——实测 MAE 从 16.96 被算成 13.21，差了 28%。
> 修正后拆成了三列：`current_aqi` / `actual_aqi_t1` / `actual_aqi_t24`，
> 名字写清楚就不会混。"

## `ApiController.java`（150 行）—— REST 接口

### 🔴 关键代码：统一响应结构

```java
private Map<String, Object> ok(Object data) {
    Map<String, Object> r = new HashMap<>();
    r.put("code", 200);
    r.put("msg", "success");
    r.put("data", data);
    return r;
}

@RestController
@RequestMapping("/api")
public class ApiController {
    @Autowired
    private AirQualityMapper mapper;

    @GetMapping("/cities")
    public Map<String, Object> cities(@RequestParam(required = false) String type) {
        List<City> list = (type == null || type.trim().isEmpty())
                ? mapper.findAllCities()
                : mapper.findCitiesByType(type.trim());
        return ok(list);
    }
}
```

**两个要点**：

1. **`@RestController`** = `@Controller` + `@ResponseBody`，返回值**直接写成 JSON 响应体**，不当视图名解析
2. **统一包一层 `code/msg/data`** —— 前端先判断 `code` 再取 `data`，比裸数组容易处理错误

> **被问到就这样答**："返回结构统一包了 code、msg、data 三层。
> 这样前端能先判断业务状态码，再取数据，比直接返回裸数组好处理错误。"

## `AirQualityMapper.java`（122 行）—— MyBatis 数据访问

### 🔴 关键代码：注解方式写 SQL

```java
@Mapper
public interface AirQualityMapper {
    @Select("SELECT city_code AS cityCode, city_label AS cityLabel, "
            + "avg_aqi AS avgAqi FROM dim_city ORDER BY avg_aqi DESC")
    List<City> findAllCities();
}
```

**为什么用注解不用 XML**：本项目查询基本都是单表聚合，注解更直观、不用维护两份文件。
**如果 SQL 变复杂**（多表 JOIN、动态条件），拆到 XML 更合适。

> **被问到就这样答**："MyBatis 有注解和 XML 两种写法。本项目的查询都是单表聚合，
> 注解更直观，也不用维护两份文件。如果 SQL 变复杂，比如多表 JOIN 或动态条件，
> 用 XML 会更合适。"

### 🔴 关键代码 2：模型指标是实时算的

```java
@Select("SELECT ROUND(AVG(ABS(pred_aqi_t24 - actual_aqi_t24)), 2) AS maeT24, "
        + "ROUND(SUM(CASE WHEN (pred_polluted = 1) = (actual_aqi_t24 > 100) "
        + "THEN 1 ELSE 0 END) / COUNT(*) * 100, 2) AS accuracyT24 "
        + "FROM fact_prediction")
Map<String, Object> modelMetrics();
```

**注意这里比较的是 `pred_aqi_t24` 和 `actual_aqi_t24`** —— 都是 t+24 时刻，时刻对齐。

> 🔴 **被问到就这样答**（证明页面数字不是写死的）：
> "页面上显示的 MAE 和准确率，是后端用 SQL 在数据库上**现场算出来的**，
> 前端不做任何计算。而且和 Python 离线训练时的报告吻合
> （16.96 vs 17.03），**两套独立计算得出同一结果，这本身就是交叉验证**。"
