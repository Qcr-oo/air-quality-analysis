# 一、项目整体与选题

### 🔴 Q1.1　为什么选这个题？创新点在哪？

**答题要点**：

- **不是"做什么"新，是"做多大"新**。空气质量研究很多，但绝大多数受限于单机算力，只做单城市或小区域。
- 本课题的差异化建立在三个规模条件上：**1233 万条真实数据 + 319 城市 + 五年跨度**，且坐标覆盖 100%。
- **真正的发现**：①污染物结构的季节反转（全量口径：PM2.5 冬季占 **71.4%** → 夏季 **26.9%**，O₃ 夏季 **28.7%** → 冬季 **0.6%**）；②城市污染分型——沙尘型（PM10/PM25 比值 **2.89**、沙尘率 13.3%）与燃烧型（AQI 最高 97.1、比值仅 1.86）在空间上清晰分离。

### 🔴 Q1.2　为什么用 Spark？用 Pandas 不行吗？

**答题要点**：

- **Pandas 是单机单线程，数据必须一次性装进内存**。1233 万行读进 pandas 约需 **4–7 GB 内存**（按 CSV 文本 1.4 GB 的 3–5 倍估），普通笔记本很容易 OOM。
- Spark 把数据切成分区并行处理，每份数据量小，可并行 + 落盘。
- **但要说实话**：Spark 有固定的启动开销（JVM 启动、任务调度，本机约 10 秒）。**数据量小的时候 Spark 反而更慢**，几十万行以下 pandas 通常更快。
- **所以本项目的价值不是"Spark 比 pandas 快"**，而是：①数据超出单机内存时 pandas 直接跑不动，Spark 能跑；②同一套逻辑，数据涨 10 倍 100 倍代码不用改；③换到真集群只要改 `master` 参数。
- **这叫「可扩展性」。**

### 🟡 Q1.3　你做的系统算"大数据系统"吗？

**答题要点**：

- 诚实说：**严格意义上它跑在单机 local 模式，不是真集群**。
- 但**具备可扩展性**：代码用的是 Spark 的分布式 API，换成 `master("spark://...")` 就能上集群，逻辑不用改。
- 数据规模（1233 万条）已经超出单机内存处理的舒适区，这是引入分布式框架的实际理由，不是"为了用而用"。

### ⚪ Q1.4　数据从哪来的？可靠吗？

- ModelScope（魔搭）公开数据集，免登录获取。
- **可靠性要说保留**：数据本身有质量问题（见第二章），我做了完整的勘察和处理。

### 🔴 Q2.1　你处理的数据有什么坑？（**必答，这是你的王牌**）

**答题要点（按这个顺序讲）：**

> "我发现并处理了 5 类数据陷阱：
>
> **第一，日期格式是「日/月/年」，不是「月/日/年」。** 这个最致命——按常规解析会丢掉 61% 的记录，剩下的日月还会对调，夏季数据跑到冬季去。
> 我是靠统计确认的：日期字符串 `A/B/YYYY` 的**第二段从来没超过 12**，说明它不可能是"日"；而**第一段有 61% 超过 12**，正好等于每月 13–31 日占 19/31。两个条件同时成立，只能是日在前。
> 最后用**月度 AQI 的「冬高夏低」曲线**做的验证——1 月 101.5、8 月 55.0，符合大气物理常识。
> （这是抽样阶段（4.9 万行）的验证值；全量口径是 1 月 102.3、8 月 55.3，方向完全一致。）
>
> **第二，有两列的列名和内容完全对调。** `pollutions` 列里装的是"优/良/轻度污染"，`quality` 列里装的是"PM25/PM10"。
> 铁证是：`pollutions` 各取值的行数与 `grade_level` 的 1–6 **完全一一对应**；而且 `quality` 列的缺失数（15,229）正好等于"优"的数量——因为空气为"优"时不存在首要污染物，字段自然是空的。
>
> **第三，2014 年只有 159 个城市**，2015 年起才是 318+。做五年趋势**必须固定城市集合**，否则口径不可比。
>
> **第四，`o3_8h` 字段缺失 31.5%**，而其他污染物只缺 4% 左右。
>
> **第五，原始数据自带重复记录。** 同一城市同一时刻出现多行，比如上海 2017 年 9036 条记录里只有 8728 个不同时刻，其中 1 月 1 日 0 点出现了 32 次。
> 这个最隐蔽——它不报错。而且它**破坏了我的滞后特征**：我用 `shift(-24)` 做'24 小时前'，但 `shift` 是按**行**移动不是按**时间**移动，有重复行时'往前 24 行'根本不是 24 小时前。
> 去重后密集样本从 554,728 行降到 537,809 行。"

**🔴 追问：重复记录为什么小样本查不出来？**

> "因为第 1 步的稀疏样本是每 250 行抽 1 行，一对重复记录**同时**被抽中的概率是 (1/250)²≈0.0016%，永远查不出来。
> **所以数据质量检查不能用抽样，必须用全量。** 这也说明我'小样本跑逻辑、全量做校验'两条路线并存的必要性。"

### 🔴 Q2.2　你怎么保证清洗是对的？

**答题要点**：

- **不能只看"没报错"**，要用一个"结果本该如此"的规律去验证。
- 对空气质量数据，最好的验证是**月度 AQI 必须"冬高夏低"**：冬季供暖 + 逆温，夏季扩散条件好。
- 我的结果是 1 月 101.5 → 8 月 55.0，标准 U 形，**说明日期解析正确**（抽样口径；全量口径 102.3 → 55.3，方向一致）。
- **如果曲线不符合规律，说明日期还有问题。**

### 🟡 Q2.3　缺失值怎么处理的？为什么不直接 dropna？

- `o3_8h` 缺 31.5%，**直接 dropna 会连带丢掉 1/3 数据**。
- 而且丢掉的很可能**不是随机的**（某些城市/年份的设备就是不报 O₃），这叫**非随机缺失**，直接删会造成偏差。
- 我的策略：**AQI 缺失才丢弃**（它是核心指标）；污染物缺失保留 NaN，分析时按需处理（pandas 的 `mean()` 会自动跳过 NaN）。

### 🟡 Q2.4　异常值怎么发现的？

- 靠 `describe()` 看 min/max。PM10 最大值 **8577** —— 强沙尘暴实测极值也就 1500–2000，**这基本可断定是数据错误**。
- **处理策略：标记而不是删除**。直接删危险——万一是真事件就丢了信息。所以我加了 `is_outlier` 列标记，把处理决定留给分析阶段。
- 实测只有 **9 行**（0.02%）超标。

### 🔴 Q2.5　处理这些陷阱的过程中，有没有踩过"二次坑"？

**答题要点（主动讲这个，比只讲陷阱本身更有深度）**：

> "有，而且这个坑比陷阱本身更值钱。
>
> **我把去重代码只加在了一条处理路径上。**
> 项目里有两个 Spark 脚本 —— `step6` 做全量清洗聚合、`step8` 做 MLlib 建模。
> 我去重只加在了 `step8`，**忘了加到 `step6`**。
>
> 后果是：全量口径的**所有**数字（年度趋势、省份排名、城市均值、污染物结构，
> 以及 Web 系统里的全部数据）都带着约 **3.2% 重复记录的偏差**，而且**不报错**。
>
> **发现方式很偶然**：对比聚类结果时，发现同样 68 个城市的平均 AQI，
> 导出的 CSV 算出 97.13，从数据库算出来是 99.55。
> **同城同数却不同值** → 说明底层数据不一致 → 顺藤摸瓜才找到漏加的去重。
>
> 修正后清洗行数从 1232.9 万降到 **1193.6 万**（移除 39.3 万行重复）。"

**🔴 追问：这个坑说明了什么？**

> "**同一条清洗规则，必须在所有处理路径上生效。**
>
> 我其实已经把清洗逻辑抽成了公共模块 `pipeline.py`，
> 但 `step6`/`step8` 是 Spark 版本、用的是 DataFrame API 而不是 `pipeline.py`，
> 于是规则被复制成了两份 —— **复制就有漏掉的风险**。
>
> 两条出路：要么强制所有路径调用同一个函数，
> 要么就必须有**交叉校验机制**。本例正是靠交叉校验才发现的。"

> 🔴 **这一段答辩时主动讲，效果很好** —— 它体现的是**工程判断力**，
> 而不是"我犯了个错"。评委见过太多只报喜不报忧的学生。

# 三、Spark 与大数据

### 🔴 Q3.1　Spark 的惰性求值是什么？

- **Transformation（`select`/`filter`/`groupBy`）不会立刻执行**，只是记录"要做什么"。
- 只有遇到 **Action（`count`/`show`/`collect`/`write`）** 才真正触发计算。
- **好处**：Spark 能把一连串操作**合并成一个执行计划**统一优化（谓词下推、列裁剪），避免中间结果反复落盘。
- **实测证据**：我读 1.89 GB 数据时，`spark.read.csv()` 那行几乎不耗时，是后面的 `count()` 才真正开始读（8.4 秒）。

### 🔴 Q3.2　什么是 Shuffle？为什么它最贵？

- **Shuffle = 把数据按 key 重新分发到不同分区**。
- `groupBy` / `join` 这类操作必须 shuffle —— 因为同一个 key 的数据原本可能散在不同分区，要算它的聚合值就得先聚到一起。
- **为什么贵**：要走**磁盘和网络**（写 shuffle 文件、再拉取），而 `map`/`filter` 这类窄依赖在同一分区内就能完成。
- **实测**：我的四项聚合里，`groupBy` 类的操作各花了 2–18 秒，而简单的 `count` 只要几秒。

### 🟡 Q3.3　`spark.sql.shuffle.partitions` 为什么要调？

- 默认值 **200**。本地跑的时候 200 个分区太碎，**每个任务数据量很小，调度开销反而拖慢速度**。
- 我设成了 **16**（约等于 CPU 核心数 × 2~4）。

### 🟡 Q3.4　为什么显式定义 schema，不用 `inferSchema`？

- `inferSchema=true` 会让 Spark **先扫一遍全量数据猜测类型**，多花一倍时间。
- 而且**可能猜错**：比如把城市编码 `110000` 猜成整数——但有些编码有前导零，转成整数就丢了。
- 我显式定义了 21 个字段的类型，**只读一遍，且不会猜错**。

### 🟡 Q3.5　Narrow dependency 和 Wide dependency 的区别？

- **窄依赖**：一个父分区只对应一个子分区（`map`/`filter`）。**不需要 shuffle，可以在同一节点内流水线执行。**
- **宽依赖**：一个父分区对应多个子分区（`groupByKey`/`join`）。**必须 shuffle**。
- Spark 靠 DAG 里的宽窄依赖划分 Stage：**遇到宽依赖就切一个新 Stage**。

### ⚪ Q3.6　RDD 和 DataFrame 有什么区别？

- **RDD**：底层抽象，面向对象，Spark 不知道数据的结构，无法优化。类型安全但慢。
- **DataFrame**：带 schema 的分布式表，Spark 能用 **Catalyst 优化器**做执行计划优化，还有 **Tungsten** 做内存布局优化。**同样的逻辑通常比 RDD 快好几倍。**
- 本项目全部用 DataFrame API（`spark.read.csv` → `groupBy` → `agg`）。

# 四、机器学习方法论 —— **这里最容易翻车，务必想清楚**

### 🔴 Q4.1　你的模型 R² 是多少？怎么评价好坏？

**答题要点**：

| 任务 | 持续性基线 | GBDT 模型 | 改善 |
|---|---|---|---|
| 提前 1 小时 | R²=0.9818, MAE=2.12 | R²=0.9849, MAE=**1.72** | MAE 降 18.9% |
| **提前 24 小时** | R²=0.3534, MAE=20.19 | R²=**0.5591**, MAE=**17.03** | MAE 降 15.7% |
| 预警分类（t+24） | 准确率 87.16% | 准确率 **88.88%**, AUC **0.9153** | — |

**关键**：**一定要同时报基线**。只报 R²=0.56 评委觉得低；说明"基线只有 0.35，模型提升了 15.7%"就完全不同了。

### 🔴 Q4.2　什么是持续性基线？为什么必须比？

- **持续性基线 = "什么都不算，直接拿当前值当作未来的预测值"。**
- 空气质量**自相关性极强**（这一小时和上一小时几乎一样），所以这个朴素基线往往强得惊人。
- **赢不了基线的模型没有存在价值。** 所有时间序列预测研究都必须报这个基线。
- 我的实测：t+24 的基线 R²=0.35，MAE=20.19；模型 MAE=17.03，**确实赢了**。

### 🔴 Q4.3　时序数据为什么不能随机划分训练测试集？

- **随机划分会把 2018 年的数据混进训练集，让模型"见过未来"**，测试分数虚高，上线就崩。
- **这叫数据泄漏。**
- 正确做法：**按时间切** —— 我用 2017 年训练、2018 年测试，**这才是真实场景：用历史预测未来**。

### 🔴 Q4.4　"用当前污染物预测当前 AQI" 有什么问题？（**经典陷阱题**）

- **AQI 本身就是污染物浓度的确定性函数** —— 取六项污染物分指数的最大值。
- 所以拿"当前污染物"预测"当前 AQI"，**本质是把这个函数拟合一遍，这叫「换算 / 单位转换」，不叫预测**。
- **为什么不算预测**：真实场景里，你要预测的那个时刻，污染物浓度本来就还不知道。
- 我实测这个"换算任务"的 R² **只有 0.66** —— 没到 0.99 是因为 `o3_8h` 缺 31.5%，而臭氧恰恰是夏季 AQI 的首要污染物。

### 🟡 Q4.5　滞后特征怎么构造？有什么讲究？

- **铁律：只能用过去预测现在。所有特征都要 `shift`。**
- **关键细节**：滚动平均必须先 `shift` 再 `rolling`：
  ```python
  s.shift(1).rolling(24).mean()   # 正确：不含当前时刻
  s.rolling(24).mean()            # 错误：包含当前时刻 → 数据泄漏
  ```
- 我用了 AQI 的 lag1/2/3/24、过去 24 小时的均值与标准差、关键污染物的 lag1。

### 🟡 Q4.6　为什么用 GBDT 而不用深度学习？

- **表格数据上 GBDT 通常优于神经网络**，这是业界的经验共识。
- **样本量**：54 万行对深度学习来说偏少。
- **可解释性**：GBDT 能算特征重要性，可以回答"模型靠什么判断"；神经网络很难。
- **训练成本**：HistGradientBoosting 在 27 万行上训练只要几秒，不需要 GPU。
- **实事求是**：项目重点在数据处理链路，不在模型创新。

### 🟡 Q4.8　K-Means 前为什么要标准化？

- **K-Means 用欧氏距离衡量相似度**。PM10 数值在 0–2000，沙尘率在 0–1。
- **不标准化的话，沙尘率的影响会被完全淹没** —— 它对距离的贡献可以忽略不计。
- 标准化后每列均值 0、标准差 1，**各特征权重才可比**。

### 🔴 Q4.9　你的城市分型是怎么做的？为什么可信？

**答题要点**：

- **先聚类、再判型，两步走**：
  1. K-Means 聚类（k=2，轮廓系数 0.3111）—— 但**聚类主要按「污染水平」分组**，因为各污染物绝对浓度高度相关。
  2. **要区分「污染类型」必须看比值**（构成指标），所以用 **PM10/PM25 比值 + 沙尘发生率**显式判型。
- **判据来自数据**：第 4 步实测沙尘天 PM10/PM25 比值 2.4，非沙尘天 1.7。沙尘是粗颗粒物，燃烧排放是细颗粒物。

| 类型 | 城市数 | 平均 AQI | PM10/PM25 | 沙尘率 | 代表城市 |
|---|---|---|---|---|---|
| 沙尘型 | 43 | 81.3 | **2.45** | **12.2%** | 和田、喀什、阿克苏 |
| 燃烧型 | 69 | **100.5** | 1.72 | 4.5% | 衡水、邢台、石家庄 |
| 一般型 | 109 | 73.7 | 1.67 | 3.0% | 日照、常州、镇江 |
| 清洁型 | 98 | **51.1** | 1.76 | 1.1% | 衢州、河池、上饶 |

- **可信的理由**：**地理分布完全自洽** —— 沙尘型全在西北（新疆/甘肃），燃烧型全在华北平原（河北/山东/河南），清洁型全在南方。**如果数据处理有错，绝不可能出来这么干净的地理规律。**

### 🔴 Q4.10　你的机器学习用的是 scikit-learn 还是 Spark MLlib？

**答题要点（这题很关键，设计方案里写的是 MLlib）**：

> "**两套都做了。**
>
> 先用 **scikit-learn** 在 31 个代表城市（53.8 万行）上快速迭代，验证特征工程和方法论 ——
> 因为 sklearn 的 HistGradientBoosting 高度优化，同样数据只要几秒，改一行跑一次很快。
>
> 确认方法论无误后，再用 **Spark MLlib** 在**全部 319 个城市（551 万行）**上重跑一遍 ——
> 因为《设计方案》里承诺的是 Spark MLlib，而且这才是'基于 Spark'这个题目应有的建模规模。
>
> **两套实现的结论一致**（都显著优于持续性基线），说明结果是**稳健的**，
> 不是某个工具的偶然产物。这在方法学上叫相互印证。"

**对比表**：

| 维度 | Step 5（sklearn） | Step 8（Spark MLlib） |
|---|---|---|
| 城市数 | 31（每省 1 个代表） | **319（全部）** |
| 训练集 | 27 万行 | **270 万行** |
| 算法 | HistGradientBoosting | GBTRegressor / GBTClassifier |
| 调参 | 未做 | **CrossValidator 网格搜索** |
| 类别权重 | 未做 | **weightCol** |
| t+24 MAE | 17.03 | **16.42** |
| t+24 R² | 0.5591 | **0.6023** |

**🔴 追问：MLlib 和 sklearn 的 API 有什么区别？**

| sklearn | Spark MLlib |
|---|---|
| `X, y` 分开传 | 用 `VectorAssembler` 把特征合成一个 `features` 向量列 |
| `model.fit(X, y)` | `model.fit(df)` |
| `model.predict(X)` | `model.transform(df)` |
| `cross_val_score` | `CrossValidator` + `ParamGridBuilder` |
| `class_weight` 参数 | `weightCol`（要先自己算权重列） |

**本质区别**：MLlib 的所有算法都要求特征放在**单个 vector 列**里，因为它是为分布式设计的。

### 🟡 Q4.11　类别权重解决了什么问题？

**答题要点**：

- **问题**：污染天（AQI>100）只占 17.5%，是少数类。不加权重时，模型倾向于**全部预测为"良好"** —— 准确率看起来不错，但污染天几乎全部漏报。
- **实测对比**：

| | 带类别权重 | 不带权重 |
|---|---|---|
| 准确率 | 0.8509 | **0.9018** |
| AUC | **0.9248** | 0.9233 |
| **污染天召回率** | **83.8%** | 56.1% |
| **漏报条数** | 62,530 | **169,494** |

- **怎么选**：**选带权重的**。预警系统的代价是不对称的 —— 误报（说污染其实没污染）代价可控；漏报（说没事结果污染了）健康受损、公信力下降，代价高得多。**宁可多报，不能漏报。**
- **这就是 precision-recall 权衡。**

> 🔴 **加分点**：如果评委问"你准确率怎么只有 0.85"，你要能接上：
> **"因为我用了类别权重。不带权重的模型准确率有 0.90，但它漏掉了 44% 的污染天。对预警系统来说，这个代价不可接受。"**

### 🟡 Q4.12　交叉验证调参的结果说明了什么？

- 最优参数 `maxDepth=6, maxIter=20`，明显优于 `maxDepth=4`（RMSE 27.43 vs 28.58），**说明模型需要一定复杂度才能捕捉非线性关系**。
- **但调参后反而略差**（MAE 16.48 vs 调参前 16.42）。**这不是 bug**，原因有两个：
  1. 交叉验证只在 **3% 子集**上做，子集最优 ≠ 全量最优；
  2. 搜索空间里 `maxIter` 只试了 {10, 20}，而调参前用的是 25，**最优值可能落在搜索范围之外**。
- **教训**：调参不是万能的，搜索空间的设计和验证集的代表性都会影响结果。

### 🟡 Q4.13　为什么 MLlib 训练比 sklearn 慢那么多？

- **数据量不同**：MLlib 用 551 万行，sklearn 用 53.8 万行（差 10 倍）。
- **实现方式不同**：MLlib 的 GBT 是**逐棵树串行**训练的（boosting 的本质就是串行），每棵树要做一次分布式直方图聚合，通信开销大；sklearn 的 HistGradientBoosting 是单机高度优化的 C 实现。
- **这就引出一个真实结论**：**Spark 擅长数据搬运与聚合，但小批量训练不一定比专门优化的单机库快。**
- 所以本项目的处理是：**数据处理与特征工程用全量（发挥 Spark 优势），模型训练用 30% 抽样（本地算力下的时间预算），模型评估用全量测试集。**

### 🟡 Q4.14　MLlib 的 K-Means 分出来的簇，和 Step 5 的一致吗？

**答题要点**：**一致，而且这是很强的证据。**

Step 8 用 MLlib 在**全部 319 城**上做 K-Means（k=4），结果是：

| 簇 | 城市数 | 平均 AQI | PM10/PM25 | 沙尘率 | 采暖效应 | 代表城市 |
|---|---|---|---|---|---|---|
| 1 | 68 | **97.1** | 1.86 | 5.2% | **43.7** | 石家庄、安阳、邯郸、邢台 |
| **2** | 26 | 86.0 | **2.89** | **13.3%** | **11.0** | 和田、喀什、阿克苏、吐鲁番 |
| 0 | 132 | 69.7 | 1.69 | 2.3% | 26.7 | 阜阳、淮南、北京、蚌埠 |
| 3 | 93 | 50.1 | 1.90 | 1.6% | 12.0 | 怀化、松原、烟台 |

**簇 2 的 PM10/PM25 比值 2.89、沙尘率 13.3%，是沙尘型；簇 1 的 AQI 最高但比值低，是燃烧型。**

> 🔴 **关键点：这是【无监督】聚类，没有给任何标签。**
> 算法自己把沙尘型（新疆）和燃烧型（河北）分成不同的簇 ——
> **说明这个分型是数据本身的结构，不是我强加的。**
> 这比"我按阈值分了个类"有说服力得多。

**🟡 追问：采暖效应这一列说明了什么？**

> "它形成了很干净的对照：**燃烧型城市（华北）采暖效应 43.7，全场最高** ——
> 因为冬季燃煤供暖叠加工业排放；
> **沙尘型城市（新疆）只有 11.0，最低** —— 因为沙尘是**春季**现象，与供暖无关。
>
> 这说明「采暖效应」是区分这两类污染的有效判据。"

> ⚠️ **补充（这个坑值得主动讲）**：这一列我最初算错了，写成了
> `avg(is_heating * AQI)`，那实际是 `avg(采暖季的AQI, 其余全是0)`，
> 被大量 0 稀释，结果全是负数（-26 ~ -49），和"采暖季 AQI 更高"的结论矛盾。
> 改成用 `when` 做条件聚合才对。
> **教训：凡是"分组算均值"，都要检查分母对不对。**

# 五、数据库与系统设计

### 🟡 Q5.1　为什么不全量导入 1233 万条明细？

- 明细导进 MySQL 会让库膨胀到几 GB，**而前端展示只需要聚合结果**（地图看城市均值、热力图看城市×月均值）。
- 所以我导入的是**聚合表**，粒度对应每张图表的需求。
- **这也是数仓的常规做法：明细留在数据湖，聚合结果进关系库供查询。**

### 🟡 Q5.2　你的表是怎么分层的？

对应数仓分层思想：

| 层次 | 表 | 回答什么问题 |
|---|---|---|
| **维度层** | `dim_city` / `dim_aqi_grade` | 「谁」「什么等级」 |
| **聚合层** | `agg_*`（7 张） | 预计算好的指标，前端直接查 |
| **事实层** | `fact_prediction` | 模型预测结果明细 |

**为什么这样分**：前端每张图表对应一张聚合表，查询就是一句简单的 `SELECT`，**不需要 JOIN 和实时聚合** —— 这叫**空间换时间**，是数据仓库面向分析查询的常规优化手段。

### 🟡 Q5.3　用 MyBatis 注解还是 XML？为什么？

- 本项目用**注解**。因为查询基本都是单表聚合，注解更直观、不易出错，也不用维护两份文件。
- **如果 SQL 变复杂**（多表 JOIN、动态条件、复杂 resultMap），拆到 XML 更合适 —— XML 支持动态 SQL 标签，且 SQL 与 Java 代码分离便于 DBA 审核。

### ⚪ Q5.4　返回的数据结构为什么包一层 `code/msg/data`？

- **统一响应结构**，前端拿到后先判断 `code` 再取 `data`，比裸数组更容易处理错误。
- 能区分**业务状态**（比如 404 用户不存在）和 **HTTP 状态**。

# 六、系统整体与可视化

### 🟡 Q6.1　整个系统的数据流是怎样的？

```
1.89 GB 原始 CSV
   ↓ PySpark 4.2（清洗 + 聚合，本机 local[*] 16 核）
8 个聚合结果 CSV
   ↓ Python pymysql（建库 + 批量导入）
MySQL 8.0（11 张表）
   ↓ Spring Boot 2.7 + MyBatis（11 个 REST 接口）
JSON
   ↓ ECharts 5.4（浏览器渲染）
可交互仪表盘
```

### 🔴 Q6.2　页面上的数字是写死的吗？怎么证明？

**答题要点**：

> "不是。所有数字都是**后端从数据库实时查询**得出的，前端不做任何计算。
>
> 我可以证明：接口返回的模型指标（MAE 16.96、准确率 89.08%）是用 SQL 在 `fact_prediction` 表上**现场算出来的**：
> ```sql
> SELECT AVG(ABS(pred_aqi_t24 - actual_aqi_t24)) AS maeT24,
>        SUM(CASE WHEN (pred_polluted=1) = (actual_aqi_t24>100) THEN 1 ELSE 0 END)/COUNT(*) AS acc
> FROM fact_prediction
> ```
> 这个值和 Python 离线训练时报告的 17.03 / 88.88% 吻合（细微差异来自数据库存的是 5 万条随机抽样，基准是全量 27.5 万条）。
>
> **前后端两套独立计算得出同一结果，这本身就是一种交叉验证。**"

### 🟡 Q6.3　为什么 ECharts 要本地化而不是用 CDN？

- **答辩现场可能没有网络或网络不稳**，CDN 挂了整个页面就白屏。
- 本地打包（1 MB 的 echarts.min.js + 569 KB 的中国地图 GeoJSON）**保证离线可用**。

# 七、局限与改进 —— **评委最爱问，提前想好**

### 🔴 Q7.1　你的项目有什么不足？

**答题要点（主动说，别等评委挑）**：

1. **跑在单机 local 模式，不是真集群** —— 代码具备可扩展性，但没有在真实分布式环境验证过。
2. **预测精度有限**：t+24 的 R² 只有 0.56。**主要原因是缺少气象数据** —— 风速、湿度、边界层高度是解释污染物扩散的关键变量，而本数据集完全没有。
3. **2014 年城市覆盖不全**，五年趋势只能用 159 个城市的子集。
4. **`o3_8h` 缺失 31.5%**，影响了臭氧相关的分析。
5. **模型只做了单点预测，没有做区间预测**（给置信区间对预警更有用）。

### 🟡 Q7.2　如果继续做，你会怎么改进？

1. **引入气象数据**（风速、湿度、气压、边界层高度）—— 这是提升预测精度最直接的路径。
2. **改用 LSTM / Transformer** 等时序模型，捕捉更长程的依赖。
3. **做区间预测**而不是点预测，给出置信度。
4. **上真集群**（或云上 EMR）验证可扩展性。
5. **加入实时数据流**（Kafka + Spark Streaming），做在线预警。
